## THE HEADLINE

Two problems Steve reported for weeks — **"it crashes and stays crashed"**
and **"branding images won't save"** — are the SAME root cause, and it is
not Railway's fault.

**Production runs Flask's development server, single-process, with eventlet
that is never monkey-patched.**

- `Dockerfile` → `CMD ["python", "run_server.py"]`
- `run_server.py:38` → `socketio.run(app, ...)` (eventlet async_mode)
- No `monkey_patch()` anywhere in `run_server.py` or `app.py`
- No gunicorn, no workers, no request timeout, no worker recycling

Under eventlet WITHOUT monkey-patching, one blocking socket freezes the
ENTIRE process — every request, forever. The process stays alive, so
Railway's `restartPolicyType: "ON_FAILURE"` never fires. Hence "stays
crashed". It is not crashed. It is **hung**.

Steve's instinct was right that it began around the EventsAir work (#240s),
for a concrete reason: **`/api/ea/status` did not exist before that.**

## PROOF (from Railway logs, 20 Aug)

```
13:38:52.686  GET /api/ea/status     <- request logged
              ...no response ever logged...
13:39 onward  only Postgres collation warnings. App never served again.
```

`/api/ea/status` (`routes/ea_survey_routes.py:752`) calls `client.health()`,
which calls `get_token()` — an outbound HTTPS call to Microsoft Entra. The
client does set `timeout=10`, but:
- `requests`' timeout does NOT cover DNS resolution, and
- under un-patched eventlet a blocking socket stalls the hub permanently.

**I triggered this outage myself** by sweeping every Organiser endpoint,
including `/api/ea/status`. Steve did nothing wrong. Worth stating plainly
because I had previously told him outages only followed merges — that was
wrong, and then I caused one while proving it wrong.

## THE IMAGE BUG — same server, same cause

```
PUT /api/settings/branding  content_length: 1605     -> 200  (text only)
PUT /api/settings/branding  content_length: 702159   -> 500
PUT /api/settings/branding  content_length: 529177   -> 500
ERROR: upsert_branding_settings error: 400 Bad Request:
       The browser (or proxy) sent a request that this server could not understand.
```

Small bodies save. Half-megabyte bodies do not. `MAX_CONTENT_LENGTH` is set
nowhere in our code, so this is not a configured limit — the body arrives
TRUNCATED and `request.get_json()` (line 8426, no `silent=True`) raises
`BadRequest`, which the handler catches and reports as 500.

The dev server does not reliably read large request bodies behind Railway's
proxy. That is why text fields persist and images vanish, and why the UI
says "saved" — the frontend gets a response, just not a success.

This also explains why my earlier curl test "proved" 4.4MB works: it did
not fail on that attempt. It is size-dependent and not perfectly
deterministic. Do not trust a single passing curl here.

## WHAT TO DO — in order

1. **Get production up right now.** Only Steve can: Railway dashboard ->
   the service -> Restart (or Redeploy). There is no Railway CLI on this
   machine. A hung process will not self-heal.

2. **Serve with gunicorn instead of the dev server.** This is the fix that
   makes both bugs go away and is the single highest-value change in the
   repo. Multiple workers mean one stuck request cannot take the site down,
   and `--timeout` kills a hung worker. Needs care: SocketIO requires the
   right worker class (`eventlet` or `gevent`) AND monkey-patching applied
   before any other import. Test locally, deploy when Steve is NOT working.

3. **Make `/api/ea/status` incapable of hanging** even after (2): it should
   not do a live token fetch on a status endpoint at all, or should cache
   the result. A status page must never block on a third party.

4. **Add a Railway healthcheck** — but read the warning in `railway.toml`
   first. Adding `healthcheckPath` on 2026-08-18 took production down and it
   had to be reverted (#219). A healthcheck is what would auto-restart a
   hung process, so it is worth retrying, but ONLY while watching the deploy
   logs live, never unattended.

5. **PR #258 (logo downscaling) is pushed and NOT merged.** It compresses
   logos to 600px instead of rejecting >400KB. Worth having, but it does NOT
   fix the image bug — a downscaled background can still exceed the size
   that breaks the dev server. Merge it only alongside (2).
